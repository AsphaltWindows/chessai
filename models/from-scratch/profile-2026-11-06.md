# Where play time goes, per model type (2026-11-06)

User question: how much time goes to move generation vs evaluation, for each model type, during play.

## Method

- **What was profiled:** `arena` with both sides the same model, 8 threads (rayon default), no `--out`.
  - Depth 0 is the self-play move choice (default policy `wld-score-jitter10`): 3 × 1000 games, seeds 1–3.
  - Depth 2 is the Nov 5 search-play move choice (`--a-policy log-odds-softmax --b-policy log-odds-softmax --temperature 0.3 --a-depth 2 --b-depth 2`): 200 games, seed 1.
  - Raw model specs (no `cal:`), as in self-play. `arena` and self-play share `selfplay::play_game`, so depth 0 here is self-play's play phase.
- **Binary:** the current working tree (including uncommitted `ht.rs`, `fm.rs`) built with debug info and frame pointers into the scratchpad: `CARGO_PROFILE_RELEASE_DEBUG=true RUSTFLAGS="-C force-frame-pointers=yes" cargo build --release --locked --target-dir <scratchpad>/prof-target`. Nothing in `rs/` or `bin/` was touched.
- **Sampler:** perf isn't installed and `perf_event_paranoid` is 2, so samply refuses to run. Instead, `sampler.c` is an `LD_PRELOAD` library:
  - Each thread gets a `CLOCK_THREAD_CPUTIME_ID` timer sending SIGPROF every 1 ms of that thread's CPU time (~1 kHz per thread, kernel tick limited). Threads created later are covered by wrapping `pthread_create`.
  - Each sample is the interrupted PC plus its callers, from glibc `backtrace()` (DWARF unwinding).
  - Addresses are resolved with `addr2line -f -i -C`, so inlined frames are expanded. Shared libraries are resolved to their nearest symbol.
  - Configurations got 5,000–42,000 samples each.
- **Categories:** walking each stack from the innermost frame outwards, the first frame matching one of these decides (patterns in `categorize.py`). Malloc/memcpy go to the category of whichever frame called them.
  - **movegen:** `legal_moves`, shakmaty `outcome`/checkmate/stalemate.
  - **make + rules:** making moves (Chess clone, `play_unchecked`, zobrist, `Game::play`) plus the rules bookkeeping (repetition, 50-move, insufficient material, `is_check`, `Game::result`).
  - **encode:** `encoding::encode`.
  - **eval:** any `::predict*`.
  - **routing:** tree routing (`leaf_from`/`leaf`, including router predictions made inside them).
  - **search/choice:** `search::*`, `player::select/choose/softmax_sample/log_odds`, sorting, RNG.
  - **lists + SAN:** SAN move-text formatting, building the candidate list, and the per-game vectors in `play_game`.
  - Samples outside `play_game` (model loading, thread start-up) are excluded from the percentages: 0.0–0.7%.
- **Counts:** a copy of the crate with thread-local counters (`profile-2026-11-06-tools/counting-build.patch`) counted plies, evaluations (candidates scored at depth 0, `Search::eval`/`outcome` calls at depth 2) and search nodes. It plays the same games: F-L's results were identical to `bin/chessai` at both depths.
  - `ns/eval = CPU time in play_game × (eval + routing share) / evaluations`. CPU time is user + sys from `getrusage`.
- **Load:** the parent's two self-play runs (`F-L-d1play-s31`, `F-L-d2play-s31`, nice 10, 8 threads each) started just before. The load average was 16 at the start and 46 at the end. These runs were at nice 0, and sampling is per thread CPU time, so the shares should hold. Absolute µs and ns are probably somewhat inflated.

Tools, run script, raw output and the counting patch are in `profile-2026-11-06-tools/`.

- 99–100% of depth-2 movegen is inside the search. Every node generates all legal moves, and about 96% of nodes are leaves (nodes ≈ evaluations + ~25 interior nodes per ply). At a leaf, the move list is only used to tell whether the game is over (mate or stalemate) before the position is evaluated.
- The root's candidates are still built (generated and encoded) at depth ≥ 1 but never scored. That costs about 1% at depth 2.
- CPU per ply is about 50× depth 0 for the flat models, and games are shorter (148 vs 251 plies for F-L).

## Training step (flat models)

Three self-play rounds each, started from the v1000 model (`self-play --init … --rounds 3 --vs-previous --no-games`, 1000 games), under the same load:

| Model | play s/round | train s/round | train share of a round |
|---|---:|---:|---:|
| CNBP (F-N) | 0.34–0.37 | 0.06–0.10 | ~15–22% |
| LR (F-L) | 0.37–0.53 | 0.30–0.44 | ~40–55% |

## Sanity check

`bench-movegen --games 2000` (single thread, random games, no evaluation) took 3.7 µs CPU per ply: encode 74%, movegen 12%, make 11%.
- Its encode : make ratio (6.9 : 1) matches F-L's arena profile (23.3 : 3.4 = 6.9 : 1).
- Its cost per ply is close to F-L's non-evaluation time per ply at depth 0 (7.2 µs × 0.50 = 3.6 µs). Random positions have more legal moves, about 1.6× by the encode cost, but none of the SAN or list overhead.

## Caveats

- **Sampling resolution:** ~1 kHz per thread of CPU time. Shares are ±1–1.5 points (2 SE) at 5,000 samples, and tighter for the larger runs.
- **Category boundaries are approximate:** inlined code is attributed by the debug-info inline chains, so boundaries between adjacent inlined pieces can blur by a point or two. For example, part of the loop that builds the candidate list is under lists + SAN.
- **Build differences:** the profiling build uses frame pointers, which costs a register, so it isn't byte-identical in speed to `bin/chessai`. Its probe timings were similar.
- **Load:** absolute times were measured under load (see Method).
