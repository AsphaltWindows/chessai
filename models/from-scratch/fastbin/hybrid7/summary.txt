WHY IT WAS SLOW (hybrid5, the tournament binary of all three running experiments)
- write_reports ran once per cycle and:
  - read all of tour/elo_history.csv (read_to_string), split every row into a Vec, copied the kept rows into a new
    String and rewrote the whole file. The file grows with the square of the cycles: rows per tournament = players
    rated by then. single-split's was 1.64 GB at cycle 821; cluster-error's 550 MB at cycle 324, ~5 GB by 1000.
  - built a dense head-to-head table over all players, retired ones included: n x n x 12 bytes (single-split
    11.5k players: 1.6 GB; cluster-error at cycle 1000, ~28k players: ~9.4 GB), and summed every row of it.
  - kept the running Elo after every tournament for every player (tournaments x players x 8 bytes).
  - ran the cold full fit (with errors) and then the 5 warm-started prefix fits one after the other.
- The tournament command also checked each retired name against all earlier ones (quadratic: 9k names = 40M string
  compares at cycle 324, ~28k names = 390M by cycle 1000).
- Peak RSS of the report-only step: 2.3 GB (cluster-error, cycle 324), 5.7 GB (single-split, cycle 858). By cycle
  1000 cluster-error's would have reached ~15-20 GB on a 30 GB machine.

WHAT CHANGED (every number computed by the same operations in the same order)
1. elo_history.csv is appended to when it is as the last call left it (history_tail): elo_history.key records
   this fit and is not older than the csv (the binary writes the csv, then the key), every tournament the key
   records still has its number of games, and the csv starts with its header, ends with a newline, has no carriage
   return in the part read, and ends with the rows of the last tournament the key records. The rows of that
   tournament are read from the end of the file (their Elo, as written with one decimal, is the warm start of the
   next prefix fit, as before). Only the new rows are made and appended. Otherwise (no key, another fit, changed
   games, a csv written after its key, a cut or odd file) the original code runs: read, keep, rewrite.
   - Why it is the same file: the original keeps the rows with tournament <= recorded (all of them, when the file
     is as left: its rows are in tournament order and end with the recorded tournament's) and adds the same new
     rows; the warm start is parsed from the same rows in the same way.
2. The cold full fit runs on a thread of its own while the main thread runs the prefix-fit chain (independent; each
   fit is the same function on the same inputs).
3. Head-to-head counts for the pairs that played only (a hash map), and each player's wins, losses and draws counted
   directly (integer sums, so the same). head_to_head.csv rows are sorted by (row player's place, column player's
   place), the original's loop order.
4. The running Elo keeps only the tournaments from the first new one on (the same arithmetic, the same order).
5. games.csv is read line by line with no vector per line and a faster name index (FxHash); any file this reader
   does not take (a carriage return, a bad line, an unknown player...) goes to the original reader, which gives the
   same games or the same error.
6. sparse_fit's pair tally uses the same fast hasher. Its iteration order only feeds the reachability search (a set)
   and lists that are sorted by unique keys before use, so the fit is the same (it already ran with a random
   SipHash seed per process).
7. The tournament command's retired-name check uses a hash set instead of a scan of the earlier names (the same
   check, the same first duplicate reported).
- CHESSAI_REPORT_TIMES=1 prints the report step's phase times to stderr (off in the league: nothing changes).
