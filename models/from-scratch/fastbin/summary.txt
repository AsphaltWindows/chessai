FAST BINARIES FOR THE NEW LEAGUE'S RECIPES (2026-11-09 ~16:25-17:15, the fast-binaries fork)

Task (the user, ~16:35: "Yeah we should update the binaries with optimizations"): every recipe of the new league
system (leagues/recipes.txt) self-plays and trains on a binary with chessai-hybrid4's three exact Q9 fast paths:
- the fast leaf test;
- lazy candidates;
- encoding from the bitboards.
Games, models and states must stay byte-identical to what each row's current binary produces.
Mapping for the engine: leagues/binaries-fast.txt. recipes.txt and the engine files are untouched.

RESULT
- 15 binaries become 5, and all 65 rows are covered. recipes.txt had 63 rows when this started; the engine added F-N
  and F-P at 17:09, and both were checked as well.
  - 57 rows, on 10 old binaries, move to chessai-hybrid4g. It is the new league's tournament binary and already
    built: hybrid4 plus the tournament's --game-cpu.
  - 8 rows on side branches move to 4 new builds:
    - chessai-dag-q9: D-L-Nc;
    - chessai-presplit-q9: T-L-Ne-pre;
    - chessai-bal-q9: T-L-Le-bal and T-L-Ne-bal;
    - chessai-bddtrig2-q9: bddfix's D-L-Ne-lreg, -rf16 and -skip, and bddtrig2's D-L-Ne-skill.
- Identity: every check of every row is byte-identical. Nothing needed an exception.
- Speed-ups (new CPU / old) grow with depth, because two of the three fast paths act only in search:
  - depth 0: 0.74-0.89 for flat models, Hoeffding trees, merge trees and the LR-probit MoE; 0.93-1.02 for the
    other trees and the mixtures, where model evaluation dominates (instructions 0.95-0.98);
  - depth 1: 0.53-0.62;
  - depth 2: 0.45-0.59 for flat models, 0.54-0.76 for trees, 0.67 for the LR-probit MoE, 0.80 for FM;
  - depth 4: 0.62-0.64;
  - training per position: unchanged, except the depth-2 label search of F-L-mix (0.58).
- CPU used: about 44 CPU min, all at nice 19 with 1-3 single-threaded jobs:
  - 2,495 s of test and benchmark runs, old and new binaries together;
  - 170 s for the 4 builds (cargo -j 2).

THE NEW BINARIES (models/from-scratch/bin; none overwritten)
- chessai-hybrid4g (md5 f934bbbc..., existing, source models/from-scratch/hybrid4g-src).
  - It replaces chessai-cyc5 (self-play) and chessai-cyc5-labels (train) on 36 rows, and chessai-resid4, -probit,
    -nbmix2, -tanroute2, -lrshare, -sparsefit, -hybrid and -hybrid3.
  - Why one binary can do this: hybrid2-src, which is hybrid3's source and hybrid4's base, descends from all of them
    through patches that each claimed identity with their options off. The checks confirm it.
- The four side branches add options the main line lacks:
  - --dag-leaves (dag);
  - --pre-split (presplit);
  - --error-target balanced (bal);
  - --delegator-split-on leaf-regret/skill, --router-forget-factor and --subrouter-target (bddfix, bddtrig2).
  Each q9 source is a copy of the branch's own source plus hybrid4-src's fast-path files. The copies are
  fastbin/<name>-q9-src; the originals (dag-src, presplit-src, balsrc, bddtrig-src) are untouched. The steps:
  - copy hybrid4-src's encoding.rs, search.rs, selfplay.rs and fastpath.rs over the branch's own;
  - add `pub mod fastpath;` to lib.rs.
  This is exactly the fast-path patch: those trees' encoding.rs, search.rs, selfplay.rs, player.rs, game.rs and
  games.rs are byte-identical to hybrid2-src's, and their Cargo.toml and Cargo.lock to hybrid4-src's. The toolchain
  is the same rustc 1.94.0. Each build was cargo build --release -j 2 at nice 19, about 40 s of CPU.
  - chessai-dag-q9 (md5 ac89ed53...) <- dag-src
  - chessai-presplit-q9 (md5 8f14315a...) <- presplit-src
  - chessai-bal-q9 (md5 583d5bb1...) <- balsrc
  - chessai-bddtrig2-q9 (md5 ae3300ad...) <- bddtrig-src. bddtrig2 is a superset of bddfix (it adds skill and
    --router-split-z), so it also replaces chessai-bddfix: bddfix's three rows are identical on it.
  Each q9 binary's train, self-play and arena --help is its parent's except for the name in the Usage line.

CHECKS
All checks ran on read-only reflink copies of cycles/runs/<lineage> (the row's first source lineage). Copies were
compared with the source after copying. Each check ran old then new, at nice 19, single-threaded, and compared every
file both wrote.

For every row:
- self-play: the row's own self-play arguments with --resume, from the row's latest live version, for 2 rounds:
  - depth 0 and depth 1: 200 games a round;
  - depth 2: 40 games;
  - depth 4: 8 games.
  Compared: the new models, the states, ladder.csv and results.txt. Versions 1 to N-2 were empty placeholders,
  because resume only checks that they exist.

For every recipe (55 recipes):
- self-play from scratch: an empty directory, no --resume, 2 rounds of 100 games, as the engine starts a new line.
- train: the engine's command line, with the latest version as --start (trees from their state):
  --model KIND --rounds 1 --seed 91 --start ... plus train_args. The fixed set fastbin/trainset holds 1,910 game
  directories, reflink copies of every 25th game of cycle 70's pool round 345, mixed plies: 161,462 positions.
- train from scratch: the same command without --start.
- version 0: leagues.py's make_version0, which trains on one empty game, with the label flags dropped.
- arenas: the latest version against the one before, both at depth 1 (40 games) and both at depth 2 (20 games).
  Policy log-odds-softmax T 0.1, --use-probs, seed 5, games saved with --out. Compared: the game files and the
  printed results, timings stripped.

For every tree recipe with a split threshold (39), splits: a fresh tree trained on the set with the row's
--split-threshold lowered to 2000. A state records its run's options, so a live state can't take another threshold.
The trees grew from 1 leaf to between 3 and 21 leaves, except T-N-Le-merge, which made no split in one round.

Flags: each old binary's train and self-play flags, parsed as leagues.py's binary_flags does, are all accepted by its
new binary with the same defaults. This matters for seeded_args, which reads the --moe-seed and --fm-seed defaults,
and for the override checks.

Thread count: one benchmark ran the new binary with --threads 2 (F-L-d1jit, 1000 games). It wrote the same files as
the old binary with 1 thread.

The benchmarks below re-checked identity too, at bigger sizes, every run against every other.

Counts (identical / checks):
- self-play: 65/65;
- self-play from scratch: 55/55;
- train: 55/55;
- train from scratch: 55/55;
- version 0: 56/56;

What the checks don't cover: option combinations that no row uses. The identity of the main-line move rests on the
code paths these rows run. A new recipe row on an old binary should get its own self-play and train check
(fastbin/sp.py and train.py, a few CPU seconds at depth 0).

SPEED
The machine is a Core Ultra 7 258V: 4 P-cores (0-3), 4 E-cores (4-7), no SMT, and the live league keeps it at load
9-12. Unpinned CPU times mix the two core speeds, so a single run at depth 0 varies by up to ±15%.

Two measures:
- bench.py: one round from the latest version, run old, new, new, old, unpinned. Robust at depth 1 and deeper.
- bench2.py: pinned to the E-cores, plus instructions retired in user space from perf stat. Instruction counts don't
  depend on scheduling. Even pinned, CPU time varies by about ±5% between runs.

Reading the tables:
- Depth 0: only the encoding applies. It saves about the same CPU per game for every kind, so its share depends on
  how cheap the model is: -15 to -26% for flat models, -3 to -5% of the instructions for trees and mixtures.
- Depth 1 and deeper: the fast leaf test and lazy candidates apply. Per game: -36 to -55% for flat models, -24 to
  -46% for trees.
- Training is the same code in old and new except for the main line's own changes: instructions 1.000-1.011, CPU
  time within the noise.
- The arenas (the new league's tournaments use hybrid4g already), pooled by kind:
  - depth 1: 0.61 probit, 0.65 LR, 0.66 NB, 0.71 Hoeffding tree, 0.74 merge trees and LR-probit MoE, 0.79 trees,
    0.82-0.86 mixtures and bdd;
  - depth 2: 0.48 probit, 0.50 LR, 0.53 NB, 0.57 Hoeffding tree, 0.66 merge trees and LR-probit MoE, 0.74 trees,
    0.82-0.86 mixtures and bdd, 0.84 FM.

NOT DONE, AND WHY
- Nothing failed identity, so nothing needed a fallback.
- No further merges:
  - bal.patch into the bddtrig2 tree would save one binary. Both patches change delegation.rs and the tree state's
    optional tail (bal adds state.rs at_end), so it is a port, not a copy.
  - dag and presplit branch from resid4, before probit. Porting their 614- and 649-line patches into the main line
    would risk identity for one row each.
  5 binaries for 65 rows looked like the right stop.
- No cyc5-labels-q9 build, which would keep cyc5's own model code for its 36 rows. hybrid4g's tree and mixture code
  executes the same or fewer instructions per self-play game (0.95-0.98 overall). In training, hybrid4g executes 0-1%
  more instructions (T-L-Le, T-L-Nc, D-L-Ne: 1.010-1.011), with CPU time within the noise (T-L-Le E-cores 1.05;
  T-L-Nc 1.00; D-L-Ne 1.02). The source tarball is cycles/chessai-cyc5-labels-src.tar.gz, whose fast-path files equal
  hybrid2-src's, so this build is trivial if training cost ever matters.
- Optional exact paths 4-6 not built:
  - 4: skip the SAN text under --no-games, about -5%;
  - 5: one legal-move list per ply, about -1.5%;
  - 6: child encodings by byte edits, ~60 lines and an assert harness.
  All three help depth-0 self-play only, the cheapest work in the system: 1-15 ms a game. Each would need a sixth
  main-line binary beside the tournament's hybrid4g, plus the whole check suite again for all 5 binaries. Worth doing
  only if depth-0 self-play becomes a large share of the new league's CPU.

THE REGRESSION: F-L-D1JIT
- The jitter policy (WldScoreJitter10) searches for an outcome at the end of each root move's principal variation
  (Search::root_outcomes). fx v2 then takes that outcome from the float model, once per search.
- At depth 1, each root move's search is a single leaf. So every leaf gets both the fixed-point value and the float
  model's outcome, which is more work than hybrid4g's single float prediction.
- Measured: instructions 1.073, E-core CPU 1.067, 1,000 games, identical games.
- At depth 2 the same scheme saves a lot (F-L-d2jit 0.39). With the softmax policy, which needs no outcomes,
  depth 1 gains too (F-L-d1play 0.62).
- F-L-d1jit is the only depth-1 jitter row. No other row uses an outcome search at depth 1 (search labels are at
  depth 2). A fix would be a source change, for example the float path for depth-1 outcome searches. I made none.
